## 适用范围

- **Pre-flight**：执行前全量检查逻辑 + 环境/代码/配置/数据是否就绪
- **In-progress**：训练/运行过程中检查日志、进度、资源、异常信号
- **Post-hoc**：实验结束后检查结果完整性、一致性、可复现性
- **Drift**：隔段时间检查"环境/代码是否有意外变化"
- **Audit**：对别人（或过去的自己）的方案进行独立评审

**不适用的场景**：
- 从零开始的方案制定（用 `plan` skill）
- 已经执行并已确认结果的简单操作

## 核心原则

1. **先逻辑后细节** —— 方案不合理时，细节检查全是浪费
2. **检查不能有副作用** —— 不能改文件、不能启动进程、不能改环境
3. **版本钉住，不只检查存在** —— 不仅要"文件存在"，还要"版本正确"
4. **区分问题等级** —— `FAIL`（必须修） vs `WARN`（建议看） vs `INFO`（仅记录）
5. **检查可追溯** —— 每次检查结果建议留存，便于后续对比 drift

## 整体结构

```
输入：方案 / 代码 / 配置 / 运行状态
        │
        ▼
  ┌──────────────────────┐
  │  Phase 1: 逻辑检查    │   "做不做 / 做得对不对"
  │  9 个检查维度         │   方案本身是否合理、是否可达目标
  └──────────┬───────────┘
             │
    ┌────────┴────────┐
    │  是否全部通过?    │
    │  ┌────┴────┐    │
    │  │ 是      │ 否  │──→ 退回修改方案
    │  └────┬────┘    │
    └───────┴─────────┘
             │
             ▼
  ┌──────────────────────┐
  │  Phase 2: 细节检查    │   "写得对不对 / 能不能跑"
  │  4 层顺序检查         │   代码、环境、文件、资源、权限逐层验证
  └──────────┬───────────┘
             │
             ▼
  ┌──────────────────────┐
  │  Phase 3: 输出报告    │   "结果和后续建议"
  │  人读 + 机读          │
  └──────────────────────┘
```
