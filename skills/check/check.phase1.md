## Phase 1: 逻辑检查

### 核心问题

> **这个方案在落地之前，逻辑上站得住吗？它真的能解决用户的问题吗？**

### 9 个检查维度

| # | 检查项 | 核心问题 | 典型反例 | 判定规则 |
|---|--------|----------|----------|----------|
| 1 | **目标对齐** | 方案是否直接解决用户提出的核心目标？ | "用户要降 FID，你改了个无关的 loss" | FAIL：方案与目标无直接因果关系 |
| 2 | **因果链合理性** | 从改动到最终结果的推理链条每一步是否站得住？ | "加大 batch size → 模型更好"——缺中间证据 | FAIL：跳跃式推理，缺失关键中间步骤 |
| 3 | **假设显式化** | 方案依赖哪些隐式假设？这些假设是否成立？ | "假设有 200G 磁盘"，"假设 checkpoint 已训练 200 epoch" | FAIL：关键假设不成立或不可验证 |
| 4 | **竞品方案** | 有没有更简单/更便宜/更快的做法？ | "为降显存搞分布式——reduce batch size 就行" | WARN：有更优方案但未评估 |
| 5 | **副作用分析** | 这个改动还会影响系统的哪些其他部分？ | "改 lr scheduler → 收敛速度变了，但没看" | WARN：明显副作用未评估 |
| 6 | **完整性缺口** | 方案漏掉了什么必要步骤？ | "做评估但没说用哪个 reference stats" | FAIL：缺必要条件步骤 |
| 7 | **风险预估** | 最可能在哪步失败？失败了回退方案是什么？ | "没想好 OOM 了怎么办" | WARN：无回退方案或风险未评估 |
| 8 | **证据等级** | 方案依据是理论分析、消融实验、还是单次观察？ | "基于一次观察就断言这是最佳做法" | INFO：记录证据强度，不直接否决 |
| 9 | **可执行性** | 方案在当前资源约束下能不能落地？ | "要 256 batch size 但 GPU 只撑得住 32" | FAIL：资源需求远超实际可用 |

### 竞品方案的边界规则

检查项 #4 只比较**同成本量级**内的方案：
- 同框架、同模型架构、同类基础设施内的替代做法
- 如果替代方案需要更换框架、加新模型、换硬件 —— 不纳入强制比较，可选择性记录
- 目的是防"为了复杂而复杂"，不是要求穷举所有可能

### 决策规则

| 条件 | 结论 |
|------|------|
| 任何 FAIL 涉及 #1（目标对齐）或 #2（因果链） | **强制停止**，必须修改方案 |
| FAIL ≥ 2 条 | **强制停止**，出报告退回 |
| FAIL = 1 条（不含 #1/#2） | **建议停止**，修改后重走 Phase 1 |
| FAIL = 0 条，WARN ≥ 3 条 | **建议修改**，但可继续进 Phase 2，标注风险 |
| FAIL = 0 条，WARN ≤ 2 条 | **通过**，进入 Phase 2 |

### 输出

逻辑检查报告，每条标注 `PASS / WARN / FAIL` + 原因。
