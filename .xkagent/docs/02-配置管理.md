# 02 · 配置管理

简体中文 | [English](02-configuration.md)

XKAgent 的配置围绕三个问题展开：在哪里工作、使用哪个模型服务，以及受限模式还能访问哪些额外路径。

## workdir：项目与运行数据的共同基准

`--workdir` 指向 XKAgent 要操作的项目目录，也是运行数据的根。例如：

```bash
python -m codes --workdir /path/to/project
```

未传参数时使用进程 cwd；相对路径同样按进程 cwd 解析，随后转为绝对路径。日志、会话等模块会在 workdir 确定后才导入，避免运行数据意外落到别处。

各目录在相关功能首次访问时自动创建：

```text
<workdir>/.xkagent/
├── historys/    # 每个会话一个 .msgz 存储文件
├── logs/        # 当前进程及历史运行日志
├── docs/        # 项目文档与按会话保存的 summary/compact
└── skills/      # 用户 Skill，同名时优先于内置 Skill
```

当仓库根就是 workdir 时，仓库文档和运行记忆会共用 `.xkagent/docs/`，但后者写入 `docs/<session>/`，不会和文档根目录中的 Markdown 文件混放。

## Provider 配置

推荐从模板开始：

```bash
cp provider.config.example .xkagent/provider.config
```

配置使用简洁的 INI 风格，键值既可写成 `key: value`，也可写成 `key = value`；以 `#` 或 `;` 开头的行是注释。一个最小配置如下：

```ini
[default]
provider: openai

[openai]
type: openai
api_key_env: OPENAI_API_KEY
base_url: https://api.openai.com/v1
default_model: gpt-4o
models.flash: gpt-4o-mini
```

`[default].provider` 是新会话的默认 Provider，`[default].model` 可进一步覆盖默认模型。每个 Provider 节可以配置：

- `type`：调用范式，支持 `openai` 和 `anthropic`。
- `api_key` 或 `api_key_env`：直接填写密钥，或指定保存密钥的环境变量。
- `base_url`：官方端点以外的兼容服务地址。
- `default_model`：该 Provider 的默认模型。
- `models.<alias>`：供 `/model` 使用的别名，如 `models.flash`。

省略 `type` 时，`default_model` 以 `claude-` 或 `anthropic/` 开头会推断为 `anthropic`，其他模型按 `openai` 处理。项目没有内置 Provider 兜底，Provider 必须在文件中有对应的非空配置节，否则查询时会明确报错。

模型值还可以携带 reasoning effort，例如 `gpt-5:high`。配置层只拆分模型名与后缀，不限制 effort 的取值，是否支持由实际 API 决定。

## 文件位置与热加载

每次查询配置时，程序按顺序选择第一个存在的文件：

1. `<workdir>/.xkagent/provider.config`
2. `<XKAgent 仓库根>/provider.config`

因此，workdir 内的配置适合项目级覆盖，仓库根配置适合作为本机兜底。环境变量只负责为已经配置的 Provider 提供 API Key，不参与寻找配置文件，也不会凭空创建 Provider。

解析结果按文件路径和纳秒级 mtime 缓存。文件保存后，下一次 Provider 查询会自动重新解析，无需重启；文件没有变化时则直接复用缓存。无法识别的非空行会报告行号，空 Provider 节会被忽略并写入警告日志。

## 妥善保存 API Key

API Key 按以下顺序解析：

1. 当前 Provider 节的 `api_key`
2. `[default]` 中的 `api_key`
3. Provider 节或 `[default]` 的 `api_key_env` 所指环境变量
4. 根据 Provider 名推导的 `<PROVIDER大写>_API_KEY`

如果都没有设置，配置层返回空值，LLM 调用时再给出配置错误。更推荐把密钥放在环境变量中：

```bash
export OPENAI_API_KEY="..."
```

```powershell
$env:OPENAI_API_KEY = "..."
```

请勿把真实密钥提交到仓库。界面和日志中的普通展示会把较长密钥处理为前三位、`***` 和末四位，但脱敏显示不能代替文件权限、环境变量和正规的密钥管理。

## 用 `permission.txt` 扩展路径范围

受限模式需要访问 workdir 之外的目录时，可编辑 `<workdir>/.xkagent/permission.txt`：

```text
/path/to/reference ro
/path/to/output ro/rw
```

`ro` 表示 `plan`、`build` 均只读；`ro/rw` 表示 `plan` 只读、`build` 可写。旧写法 `read`、`write` 仍兼容，分别等价于 `ro`、`ro/rw`。

解析时会忽略空行和 `#` 注释。格式错误、权限值未知或路径不存在的条目会被跳过；`~` 会展开，相对路径按进程 cwd 转为绝对路径，而不是按 workdir 解析。同一路径出现多次时，以最后一条为准。

修改后运行 `/mount refresh` 即可重载。`permission.txt` 只扩展 `plan`、`build` 的受限路径范围：`plan` 仍然只读，`build-unsafe` 不以这份文件作为访问边界，并仍保留运行时对 `.xkagent` 数据目录等少量保护。动态挂载与完整沙箱语义见[沙箱与工具执行](05-沙箱与工具执行.md)。

## 从源码继续阅读

`codes/config.py` 负责 workdir 和运行目录；`codes/provider_config.py` 实现配置查找、解析、缓存及模型选择；`codes/agent.py` 解析 `permission.txt` 并维护动态挂载。可用字段与示例以 `provider.config.example` 为准。
